# 架构演进决策（模块化服务 vs 真微服务）

## 背景

当前形态是“按能力拆分进程 + 共享 PostgreSQL”。这能提供一定部署弹性，但在数据边界、跨服务耦合和独立演进上仍偏向模块化单体。

## 方案对比

### 方案 A：继续共享库的模块化服务（现状增强）

- 适用条件：
  - 团队规模较小，优先稳定交付与研发效率。
  - 暂无强隔离诉求（合规、租户隔离、异地高可用）。
- 要做的增强：
  - 明确仓储访问边界：每个服务只访问自己的表集合。
  - 网关去本地回退链路，统一通过服务调用。
  - 引入事件总线（至少 Outbox）降低同步耦合。
- 优点：
  - 成本低、改造快、排障简单。
- 风险：
  - 服务自治和独立发布能力上限有限。

### 方案 B：演进为真微服务（每服务独立数据边界）

- 适用条件：
  - 多团队并行开发，发布频率高。
  - 需要独立扩缩容、独立 SLO 与数据权限隔离。
- 必要前置：
  - 每服务独立数据库（或至少独立 schema + 强约束）。
  - 跨服务改为 API/事件协作，禁止跨库直连。
  - 建立数据一致性机制（Saga/补偿、幂等、重试、死信）。
- 优点：
  - 自治性和扩展性更高。
- 风险：
  - 运维复杂度、链路成本、一致性治理成本显著上升。

## 决策门槛（满足 3 项再进入方案 B）

- 两个以上团队需要独立发布节奏。
- 至少一个域需要单独扩缩容且负载差异明显。
- 存在明确合规/安全边界要求（按域隔离数据权限）。
- 当前共享库模型已成为交付瓶颈（跨域改动冲突频繁）。

## 建议路径

1. 立即执行：先按方案 A 强化边界（低风险高收益）。
2. 观察 1-2 个版本周期：用发布频率、故障范围、跨域变更比例做评估。
3. 达到门槛后：按域分批迁移到方案 B（优先 detection/report，再治理域）。
